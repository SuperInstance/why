## Finding 1 — Inferred edges confer liveness (spec violation)

`docs/format.md` states the core trust rule: *"Inferred edges never confer
liveness… a node whose only path to a live root runs through an inferred edge
is `unknown`, not `alive`."*

`why-core/src/reach.rs` pass 1 propagates `Alive` over reverse edges while
discarding provenance (`for (parent, _)`), so inferred edges confer liveness
exactly like explicit ones.

Reproduction:

```
# graph.txt
node:a -> root:live (inferred)

# att.txt
root:live alive 2024-01-01 probe
```

```
$ why check graph.txt --alive att.txt
alive node:a        <-- spec requires: unknown
alive root:live
```

The lab already tracks this as a v0.2 blocker (why-lab D-006), but the
shipped v0.1 behaviour contradicts the spec today, and the README presents
the trust rule as current behaviour. Anyone gating on v0.1 output gets
silently wrong `alive` verdicts on precisely the case the tool exists to
distrust.

## Finding 2 — Deadness does not propagate past one hop (false reassurance)

`docs/format.md` defines `dead` as: *"Full traversal completes; no such path
exists [to a live root]."* A chain whose every root is attested dead should
therefore read `dead` at every depth.

`reach.rs` pass 2 instead treats **any unattested node that appears as a
parent** as an unknown-source and floods `unknown` down its subtree before
pass 3 can mark anything dead. Only roots are attested; intermediate nodes
never are — so any dead chain of depth ≥ 2 degrades to `unknown`.

Reproduction:

```
# graph.txt
leaf:x -> mid:y (explicit)
mid:y -> root:dead (explicit)

# att.txt
root:dead dead 2023-04-12 probe
```

```
$ why check graph.txt --alive att.txt
unknown leaf:x      <-- spec requires: dead
unknown mid:y       <-- spec requires: dead
dead root:dead
exit code: 0        <-- a fully dead graph passes CI
```

This is the dangerous direction: `unknown` does not fail `check` (exit 0),
so a repository whose deadness is all two-or-more hops deep reports clean.
The shipped demo exhibits it: `workflow:deploy#build` and
`workflow:deploy#test` sit under the dead `project:MIG-4821` yet read
`unknown`, not `dead`.

Suggested direction (reviewer's note, not a prescription): pass 2 should
only seed `unknown` from parents whose subtree is *not* fully resolved —
i.e. propagate dead upward from attested-dead roots through explicit chains
first, and reserve `unknown` for nodes that can reach a parent with no
attested root anywhere beneath it. The four-state table in the spec already
describes the intended result; the corpus needs a depth-2 dead pair as a
golden test.

This finding is **not** in why-lab's blocker list (D-006 covers Finding 1,
coverage, staleness, ID resolution, ticket anchoring — not this). It was
found by external probe, which is the audit working as intended.

## Minor observations

- `extract` only recognises inline `needs:` (`needs: [a, b]` on one line).
  Block-style `needs:` lists — common in real workflows — produce no edges.
- `why-core/src/parse.rs` reads attestation fields positionally
  (`parts[2]` = since, `parts[3]` = by). The draft v0.2 fields (`until`,
  `review-by`), if written into an att.txt today, would be silently misread
  as `by`. Worth a strict-mode rejection before v0.2 ships those fields.
- `chain()` explains dead/unknown nodes by walking only the *first* parent
  edge, so a multi-parent node's printed "because" can omit the parent that
  actually determined its status.
- `why-lab` is private while `why` is public: the receipts that make this
  project's process credible are not visible to outside readers. (Noted, not
  judged — the lab contains digests of private ideation; visibility is the
  owner's call.)

## Verdict

The engine is real, the format is sound, the lab's self-audit culture is
unusually good, and the v0.2 blocker list is honest — with one hole
(Finding 2) and one spec rule (Finding 1) that should be treated as
correctness, not roadmap. The open product question remains the one the
playtest identified: without an attestation bootstrap, cold repos return
100% unknown and the tool cannot produce a finding. That is an adoption
gap, not a correctness gap.
